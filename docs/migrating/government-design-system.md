# Switching from a government design system

For teams whose services use a public-sector design system that follows the common pattern: a prefixed class-name
convention (for example `app-button` or `app-header__logo`), a stylesheet and scripts you include, and components copied
or imported as HTML. This guide says what changes, in what order, and what to check. It names no particular system,
because the mapping is the same shape for all of them.

Lily is not an official design system and does not replace your organisation's standards or its identity. Decide with
your design and governance owners before you start; a migration is a service change, not only a code change.

## Adopt alongside, then migrate

Do not start by replacing everything. Work in three stages, and stop at any of them.

1. **Alongside.** Keep your current components. Add a Lily theme and the helper packages that have no equivalent (the
   theme, language and text-size pickers, the date-time picker, the data grid, the label packs). Nothing is removed.
2. **One journey.** Pick a low-risk journey (a search page, a settings form) and rebuild it with Lily components.
   Compare it in front of your users and your accessibility specialists before going further.
3. **Everything else.** Move the remaining components one family at a time (forms, then navigation, then layout), keeping
   each release shippable.

## What changes

| Concern           | Government system pattern                | Lily                                                                                                  |
| ----------------- | ---------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Class names       | A prefix and BEM modifiers on every part | One kebab-case base class per component (`button`, `summary-list`) and stable sub-classes             |
| Styling           | One shipped stylesheet                   | A theme file you choose, or your own; the components ship no CSS                                      |
| Variants          | Modifier classes (`--secondary`)         | `data-` attributes and the theme's rules; no colour classes in markup                                 |
| Tokens            | Sass variables                           | CSS custom properties (`--color-primary`, `--lily-space-md`); a brand overlay re-colours a base theme |
| Scripts           | One bundle that initialises components   | Behaviour is in each framework component, or a small custom element; no global initialiser            |
| Content and text  | Often default English in the component   | None: every string is a prop, so translation is the consumer's                                        |
| Frameworks        | Plain HTML and one templating language   | The same catalogue in HTML, Svelte, React, Vue, Angular, Blazor, Nunjucks, Solid and Web Components   |
| Identity and logo | Part of the system                       | Never shipped. Supply your own logo as a link to the home page, and your own fonts                    |

## Steps

1. **List what you use.** Search your templates for the prefix and list each component you use, with how many pages use it.
2. **Map it.** Use the table below. Every row names real catalogue slugs; a generator fails if one does not exist.
3. **Choose a theme.** Start from the closest reference theme and check its contrast. A brand overlay of at most twenty
   declarations re-colours it without forking.
4. **Rebuild one journey** (see above), including its error states and its empty states.
5. **Run your own checks.** Keyboard only; a screen reader your users use; 320 CSS pixels wide; 400 percent zoom; the largest
   text size; a right-to-left language if you serve one. Lily's automated tests do not replace this.
6. **Migrate by family**, deleting the old stylesheet rules for a family when its last use is gone.
7. **Record what you decided**, so the next person does not reopen it.

## Rough effort

Estimates, not measurements: they come from the number of components in the table, not from a migration we have run.

| Size of service                         | Components in use | Likely effort                                                           |
| --------------------------------------- | ----------------- | ----------------------------------------------------------------------- |
| A content site                          | 8 to 12           | A few days for the theme and templates, longer for testing              |
| A transactional service (forms, a grid) | 20 to 30          | Weeks, mostly in forms and error handling                               |
| A large multi-team portfolio            | 30 or more        | A programme: plan by journey, and expect to maintain both for some time |

## What Lily does not do for you

- It does not ship your organisation's logo, fonts, content or legal pages.
- It does not make a service accessible: it gives you components with the right semantics, and tests for them. The
  service still needs its own audit. See the [accessibility statement](../accessibility-statement.md) for what is and is not
  verified.
- It does not replace research with your users. A component that works for one service may not suit yours.
- It has no support contract today, and one maintainer. Treat that as a risk and write it into your decision.
