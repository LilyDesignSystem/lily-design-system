# Lily Design System™ production audit for healthcare

**26 November 2026 · Engineering review with synthetic records**

**Decision.** Use Lily for a bounded pilot with a named clinical owner, a pinned package version and a defined workflow. Hold clinical use of the tutorial’s allergy importer and the affected allergy-list and result-display patterns until their behavior is verified in the adopting application. Include the repaired patient-selection journey in that verification. Lower-risk components such as a button or a field label can be assessed separately. The first outstanding repair is in the IPS tutorial. A document that rules out food allergies can appear to rule out every allergy.

The audit observed synthetic demonstrations and local renders. It did not measure incident likelihood or establish patient harm.

### 1. Follow the selected person all the way to the destination

In Chromium, I searched for **Okafor**, selected **Open record for Chidi OKAFOR, 12 Jul 1990**, and read **EXAMPLE, Alexandra, born 3 February 1949** in the destination banner. The source link contained the synthetic NHS number ending in **5870**. The banner showed the number ending in **5919**. The search and summary had separate fixtures. The destination initialized to patient A regardless of the link. The search test at the audited revision stopped after verifying the matching row. The summary’s separate test exercised its own switcher. Both tests missed the handoff. Putting the number in the query string also contradicted the project’s guidance on history and logs. [Search at the audited revision](https://github.com/LilyDesignSystem/lily-design-system/blob/a9761da28d123fc2d02081b5377c2ce56f90fdce/lily-design-system-svelte-sveltekit-examples/src/routes/find-patient/%2Bpage.svelte) · [Summary at that revision](https://github.com/LilyDesignSystem/lily-design-system/blob/a9761da28d123fc2d02081b5377c2ce56f90fdce/lily-design-system-svelte-sveltekit-examples/src/routes/patient-summary/%2Bpage.svelte) · [Lily privacy guidance](../../../PHI.md)

**Follow-up during review.** Commit `5c5cd7d4d` introduced one fixture, opaque keys, an unknown-key state and click-through tests. Its 38 Chromium clinical tests passed, but a separate regression probe still found Alexandra under an old `?nhs=…` bookmark. Commit `fb5b99cd8` sends those links to the recovery state. On a fresh isolated build with that repair, all 38 project checks and the additional historical-link probe passed in Chromium. In a real service, authorize the selected record on the server and bind the banner, data fetches and actions to the same record context. [Current search](../../../lily-design-system-svelte-sveltekit-examples/src/routes/find-patient/+page.svelte) · [Current summary](../../../lily-design-system-svelte-sveltekit-examples/src/routes/patient-summary/+page.svelte) · [US SAFER Guide on patient identification](https://healthit.gov/resources/2025-safer-guide-patient-identification/)

**Acceptance test.** Follow each synthetic search result, including the two people with the same name and birth date. Match the number and demographics across the selected row, destination banner and clinical contents. Repeat on reload and browser Back. Unknown and legacy keys must show a recovery state without displaying anyone’s clinical data. Check the generated link and captured request URL for the synthetic health identifier.

### 2. Preserve the scope and coding system of allergy statements

I ran the tutorial’s own `readSummary` function against variations of its example bundle. A sole `no-known-food-allergies` entry produced exactly the same output as `no-known-allergies`. The output had status `none-known`, an empty entries array and no conflict. The page labels that state “None known” under “Allergies and intolerances”. A reader has lost the distinction between food and medication allergies. The corresponding IPS code system explicitly distinguishes these concepts. [Tutorial source](../../../lilydesignsystem.github.io/src/lib/pages/tutorials-international-patient-summary/en.html) · [HL7 IPS absence-code definitions](https://hl7.org/fhir/uv/ips/CodeSystem-absent-unknown-uv-ips.html)

Two further probes exposed the same problem at the coding boundary. Prepending a local coding before the existing LOINC allergy-section code changed the section to `omitted` and dropped both entries. Giving an empty section a local code spelled `nilknown` produced `none-known` despite its different coding system. The tutorial selects the first populated code in both places. FHIR permits multiple codings and gives their order no semantic meaning. [Executable tutorial text, steps 3–5](../../../lilydesignsystem.github.io/static/tutorials/international-patient-summary.md) · [FHIR R4 CodeableConcept](https://hl7.org/fhir/R4/datatypes.html#CodeableConcept)

**Recommended change.** Match the expected system and code across all codings. Preserve scoped negative assertions as entries with their scope. Reserve the section-wide negative state for an explicit recognized assertion about the whole section. Preserve unknown coding as unresolved information. Run the actual code copied from the tutorial with a medication allergy alongside “no known food allergies”, swapped coding orders and a colliding local code. The medication allergy must remain visible, the food statement must retain its meaning and reversing coding order must preserve the output.

### 3. Verify the subject of a clinical entry before placing it under a banner

In a second synthetic bundle I kept the composition’s patient unchanged, added a second patient and pointed the first allergy’s `patient.reference` at that person. The tutorial returned the original patient and a known-allergies section containing the second person’s allergy. It resolves the composition subject and independently resolves the section entries. It never checks that those two identities agree. This concerns the tutorial’s reader and the claims made for that reader. It does not establish a fault in Lily’s headless list component. [Tutorial reader and renderer](../../../lilydesignsystem.github.io/static/tutorials/international-patient-summary.md) · [FHIR R4 definition of AllergyIntolerance.patient](https://hl7.org/fhir/R4/allergyintolerance-definitions.html#AllergyIntolerance.patient)

**Recommended change.** For each resource type the tutorial presents as personal history, resolve its patient or subject against the document patient. Give missing, unresolved and conflicting subjects an explicit outcome agreed with a clinical reviewer. For supported information about relatives, preserve the relationship and label whose history it is. Test a two-patient bundle and a valid bundle using two reference forms for the same patient. A conflicting allergy must never appear as the banner patient’s own.

### 4. Resolve “none known” conflicts before sending HTML

Using the local React package entry point and `renderToStaticMarkup`, I passed `AllergyRecordList` a status of `none-known`, words for that state, a `conflictLabel` and one synthetic active entry. The HTML contained **No known allergies** in the list name and first item, followed by **Example allergen**. The React hook initializes entry presence to false and learns it from the mounted DOM. Slow hydration or a static consumer can therefore expose the contradiction. Lily documents this limitation. The healthcare register nevertheless describes HC-C17 as tested, with a stronger promise than the server render delivers. [React hook](../../../lily-design-system-react-headless/components/use-record-list.ts) · [List contract and server caveat](../../../components/allergy-record-list/index.md) · [HC-C17](../../../spec/healthcare-ui/requirements.md)

**Recommended change.** Let an adapter derive the status and active-entry count from the same data before rendering. Make the parent IPS section consume that same decision. While composition is ambiguous, require an explicit resolved status or a neutral conflict message. Keep the active entry visible for reconciliation. Test the response HTML, hydrated DOM, JavaScript-disabled view and print output. Check visible text and the accessible list name for active, refuted and entered-in-error entries. Record the rendering modes covered alongside the requirement.

### 5. Carry critical and corrected result meaning into production text

In a React production render, `interpretation="HH"` with no `flagLabel` left the code in `data-interpretation` with no corresponding flag text. Adding `status="corrected"`, a valid status label and a `previousValue` without `previousLabel` emitted the current value, a bare number in `<del>`, and the word “Corrected”. The type permits both omissions. A theme can color the flag and strike through the earlier number, while copied text loses both cues. These are consumer input errors the public API accepts. No screen-reader speech was measured. The existing code already checks non-final status wording before rendering a result, which gives maintainers a precedent. [React implementation](../../../lily-design-system-react-headless/components/ObservationView.tsx) · [Canonical contract](../../../components/observation-view/AGENTS.md) · [WCAG 2.2 use of color](https://www.w3.org/TR/WCAG22/#use-of-color)

**Recommended change.** Model a superseded value and its label as a pair. Validate that abnormal interpretations have readable localized words at the adapter boundary, including blank translations and untyped input. Agree with the laboratory service how to display an incomplete mapping while keeping the verified current value available. Test the current value, previous value and abnormality as plain text, in print and during a spoken review. Include the clinical owner, amendment time and follow-up state in the composed workflow. The observations example already distinguishes seeing a correction from acknowledging it and completing follow-up. [Corrected-result example](../../../lily-design-system-svelte-sveltekit-examples/src/routes/observations-chart/+page.svelte) · [US SAFER Guide on test results and follow-up](https://healthit.gov/resources/2025-safer-guide-test-results-reporting-and-follow-up/)

## Production evidence and its limits

**Safety engineering.** Keep the permanent requirement IDs, patient-scoped handover rehearsal, worked hazard log and distinction between display and clinical calculation. The requirement checker found 49 IDs, including 41 marked tested. The row-by-runtime matrix helps an adopter identify exactly where to ask for more evidence. Add the first five findings above to the existing hazard log with a named owner, the affected release, how a user would encounter the failure, the local mitigation and the evidence used to close it. For an NHS England deployment, the supplier and deploying organization should establish how DCB0129 and DCB0160 apply to their respective work. [Worked hazard log](../../assurance/hazard-log-example.md) · [Healthcare register](../../../spec/healthcare-ui/requirements.md) · [NHS England clinical risk management standards](https://digital.nhs.uk/services/clinical-safety/clinical-risk-management-standards)

**Accessibility and language.** The generated Core report lists 40 of 40 candidates with automated keyboard/ARIA and cross-engine test evidence, zero meeting the human screen-reader criterion and zero Core members. The self-assessed ACR describes its Playwright method as Chromium only. Generate both accounts from the same evidence and distinguish configured coverage from an executed result. The assurance pack also records 63 of 64 label packs as lacking native-speaker review. For the first deployment, have a clinician and an experienced assistive-technology user identify the patient, distinguish a scoped negative allergy from a global one, and identify the current corrected result. Use the target language, theme and device. Record what participants actually identified, the announcement and any recovery. Re-run the failed task before sign-off. [Core evidence](../../core.md) · [ACR](../../accessibility-conformance-report.md) · [Assurance pack](../../assurance/index.md) · [WCAG 2.2 complete processes](https://www.w3.org/TR/WCAG22/#cc3)

**Privacy.** The source checks passed for 94 identifier views and 94 inputs across ten catalogs. The PHI inventory check passed for 73 attributes across 30 components. The latter reads canonical Svelte markup and explicitly excludes spread attributes and values passed through children. The search link illustrates a different exposure path in composed pages. In the adopter’s staging configuration, carry distinct synthetic identifiers through search, selection, a patient switch and an error. Inspect request URLs, error events and configured replay exports for those values. Assign a privacy owner to verify the actual capture settings. [PHI inventory](../../../phi-attributes.tsv) · [Checker scope](../../../bin/check-phi-attributes) · [Adopter responsibilities](../../../PHI.md)

**Release and operations.** The release workflow defaults to a dry run, checks package metadata and supports provenance. A real workflow dispatch has no dependency on a successful clinical test run for the same commit. The publish script applies its local receipt gate only outside CI. The changelog also distinguishes prepared fixes from releases. Make a real publish consume evidence for its exact commit and the actual package archive. Include clinical suite results, explicit skips, affected and fixed versions and the archive digest. Exercise a failed gate in dry-run mode. A hospital team should retain its last verified artifact and rehearse rollback with the same patient-selection and result-correction cases. [Publish workflow](../../../.github/workflows/publish.yml) · [Headless publish script](../../../bin/publish-headless) · [Release history](../../../CHANGELOG.md) · [Existing release and transition work](../../../tasks.md)

## Order of work

1. **Before the next healthcare tutorial release**, fix allergy-code interpretation and subject resolution in the reader. Add the fixtures from findings 2–3 to its executable examples. Keep the repaired search-to-summary journey in the example app’s release checks.
2. **Before piloting a clinical screen**, choose one runtime, locale, theme and exact package version. Run the server-render, corrected-result and medicine cases on its build. Have the clinical owner approve the wording for conflicts and incomplete mappings. Record a decision for each unresolved hazard.
3. **Before live use**, complete the observed accessibility and clinical tasks, exercise real staging telemetry with synthetic records, and retain the verified artifact and rollback result. Repeat the affected scenarios when a renderer, terminology mapping, translation, theme or package version changes.
