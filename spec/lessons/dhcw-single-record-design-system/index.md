# Lessons from the DHCW Single Record Design System

**Give an empty allergy list an explicit meaning before rendering it.** In both Single Record’s React banner and Lily’s SvelteKit patient summary, an empty array can produce a positive statement that the patient has no known allergies or adverse reactions. Lily already has the vocabulary to distinguish unavailable information from a confirmed negative. The immediate change belongs in the example’s data contract. ## P59-T1 · Carry allergy status from the record to the screen

Single Record keeps patient identifiers visible when its banner collapses. Its React component also defaults the `reactions` prop to an empty array and prints “No known adverse reactions” when the expanded list has no entries. A caller omitting the prop gets the same text as one supplying a reviewed negative. Lily’s patient banner already has identity and narrow-screen checks. The overlooked case is in its patient summary, where both the section and the list derive their status from `patient.allergies.length`. [Single Record implementation](https://github.com/DHCW-Digital-Health-and-Care-Wales/single-record-design-system/blob/207cacf35a3e70de63db2553cbb8b1df9f2dcb57/packages/react/src/patient-banner/PatientBanner.jsx) · [Lily patient summary](../../../lily-design-system-svelte-sveltekit-examples/src/routes/patient-summary/+page.svelte) · [Banner tests](../../../lily-design-system-svelte-sveltekit-examples/e2e/patient-banner.spec.ts)

Add explicit status to the existing synthetic records. Use it for both the section and list, and keep one owner for the visible status words. Make three fixtures with identical empty arrays and different evidence: reviewed and none known, never recorded, and source unavailable. Switching between them should change the text and semantic status together. A fourth fixture with an entry should still show the substance and reaction. P55-T2 addresses the scope of a *coded negative* in the IPS adapter. This proposal addresses how the demo interprets the *absence of entries*. ## P59-T2 · Find a patient by number and let staff choose the match

Single Record’s patient-search pattern is marked **in review**. It describes quick lookup by identifier, an expanded demographic search and an explicit choice even after a wristband scan returns one result. The case-note prototype illustrates the interaction, but its submit handler returns a fixed result set. Lily can demonstrate actual matching against its local fixtures. Its current screen supports name prefixes, distinguishes two patients with the same name and birth date, and opens the selected record through an opaque key (P53-T1). [Search guidance](https://github.com/DHCW-Digital-Health-and-Care-Wales/single-record-design-system/blob/207cacf35a3e70de63db2553cbb8b1df9f2dcb57/patterns/patient-search/guidelines.md) · [Case-note search implementation](https://github.com/DHCW-Digital-Health-and-Care-Wales/single-record-design-system/blob/207cacf35a3e70de63db2553cbb8b1df9f2dcb57/products/case-note-tracking/prototype/src/PatientSearch.jsx) · [Lily find-a-patient route](../../../lily-design-system-svelte-sveltekit-examples/src/routes/find-patient/+page.svelte)

Add an exact NHS-number lookup alongside name search. Reuse Lily’s identifier input and validator. Accept digits with or without grouping spaces, retain the entered value on error and distinguish an invalid number from a valid number with no local match. A successful search should focus the result count and let the user compare the identity details before following the existing link. Test with the keyboard using synthetic numbers and keep the number out of URLs. Camera access, a matching service and a clinical record backend are unnecessary for this pilot. ## P59-T3 · Use one Welsh name to test the whole journey

Each Single Record synthetic patient has a reason to exist. One exercises a Welsh circumflex and a lower-case surname particle, another an apostrophe. Its generator derives check digits and calculates ages at a fixed reference date. Its content decision record also distinguishes a published data definition, a rule about display, and a local decision. That distinction matters here: DHCW chooses a `999` demo prefix, while the NHS service manual permits example numbers beginning with 9. Lily’s `943` examples already fit the published guidance. [Fixture generator](https://github.com/DHCW-Digital-Health-and-Care-Wales/single-record-design-system/blob/207cacf35a3e70de63db2553cbb8b1df9f2dcb57/scripts/demo-patients.mjs) · [Content decision](https://github.com/DHCW-Digital-Health-and-Care-Wales/single-record-design-system/blob/207cacf35a3e70de63db2553cbb8b1df9f2dcb57/decisions/DDR-037-published-sources-supersede-ui-standards.md) · [NHS guidance on example numbers](https://service-manual.nhs.uk/design-system/patterns/ask-for-nhs-numbers)

Extend Lily’s shared fixture rather than inventing another patient in each page. Give a Welsh synthetic patient a mixed-case family name and an accented given name. The current search uppercases the family-name query and compares it to the stored spelling as-is, which works for the existing uppercase fixture surnames. Compare consistently on both sides, preserve the supplied spelling for display, and exercise composed and decomposed Unicode input. Test the result row, its accessible link name and the selected summary. This gives P53-T1 a regression case it currently misses without changing how the same-name patients are distinguished.
