Ano ang ibig sabihin ng “tinatarget ang WCAG 2.2 AAA” dito

Ang salitang tinatarget ay sinadya. Sinasabi ng pahinang ito nang eksakto kung ano ang napatutunayan, gamit ang ano, ano ang hindi napatutunayan ng anuman, at ano ang balak naming gawin sa puwang. Hindi kailanman nagke-claim ang Lily ng “pagsunod” sa WCAG — walang audit na sumusuporta rito.

Napatutunayan, tuloy-tuloy

  • Ang canonical na semantic element ng bawat component, mga attribute ng ARIA, at class hook — pinatutunayan ng mga unit suite bawat framework (mahigit 15,000 kaso sa pitong framework).
  • Ang bawat isa sa 571 demo page ng component sa SvelteKit example app ay axe-clean (mga rule set ng WCAG 2.0/2.1 A+AA at 2.2 AA) — ang buong sweep ng catalog, unang na-baseline noong 2026-08-27 at muling pinatakbo noong 2026-10-06 — kasama ang mga baseline bawat app sa home, catalog, at composed na ruta sa lahat ng pitong example app.
  • Mga kontrata ng keyboard para sa bawat interactive na component, dokumentado sa canonical na metadata ng bawat component at sinusubukan ng mga suite; ang mga helper package ay nagpapatakbo rin ng mga Playwright spec sa tunay na browser.
  • Mga floor ng target-size ng WCAG 2.2 at overflow guard sa lahat ng 57 tema; skip-link, landmark, at walang pahalang na overflow sa apat na viewport bawat app; lang/dir application at ang RTL flip.

Hindi napatutunayan ng anuman

  • Wala pang conformance audit na naisagawa kailanman. Walang VPAT, walang sertipikasyon. Sinasaklaw ng mga automated na tool ang minorya ng mga success criteria ng WCAG.
  • Ang mga criteria na partikular sa AAA (pinahusay na contrast, at iba pa) ay mga layunin ng disenyo, hindi mga napatunayang katangian; ang mga rule set ng axe ay A/AA ang pinapatakbo. Wala pang nakalaang high-contrast na tema.
  • Halos hindi pa nasusubukan ang gawi ng screen-reader. Pinatutunayan ng mga suite ang mga attribute ng ARIA, hindi ang ibinabalita ng VoiceOver, NVDA, o JAWS — at higit sa isang beses nang nagpadala ng berdeng mga suite ang proyektong ito sa ibabaw ng tunay na mga depekto, na bawat isa ay isinulat sa changelog dahil mismo hindi sila nakita ng mga suite.

Ano ang balak naming gawin tungkol dito

Ang independiyenteng accessibility audit ang unang pinangalanang gamit ng anumang pondo ng proyekto, at nakahanda na ang saklaw na kailangan ng auditor. Hanggang doon, ang mga ulat ng screen-reader ang kontribusyong pinakagusto ng proyektong ito: “ang component X ay nagbabalita ng Y, na mali dahil sa Z” ay direktang magagawan ng aksyon.

Mag-ulat ng problema

Magbukas ng issue sa github.com/LilyDesignSystem/lily-design-system o mag-email sa joel@joelparkerhenderson.com. Nakakatulong ang pagbanggit ng criterion ng WCAG pero hindi kinakailangan — ang “Hindi ko magamit ang X gamit ang keyboard” ay kumpletong ulat.

Ang buong pahayag, kasama ang talaan ng pagpapatunay at kasaysayan ng pagsusuri nito, ay nasa repository: docs/accessibility-statement.md.
