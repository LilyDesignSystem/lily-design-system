# Lily Design System tools

The `bin/` scripts and the Makefile, one line each. Part of the [AGENTS/lily.md](lily.md) set.

- [Makefile](../Makefile): `make publish-github-pages` delegates to [bin/publish-github-pages](../bin/publish-github-pages), see [spec/monorepo-github-pages/index.md](../spec/monorepo-github-pages/index.md)
- [publish-github-pages](../bin/publish-github-pages): Push `lilydesignsystem.github.io/` to its own repository via git subtree (the one subproject that still has one; it serves GitHub Pages)
- [test-github-discussions](../bin/test-github-discussions): Verify the organization's GitHub Discussions page exists and the source repository's discussions redirect to it (`make test`); see [spec/github-discussions-for-organization-repository/index.md](../spec/github-discussions-for-organization-repository/index.md)
- [list-components-as-kebab-case](../bin/list-components-as-kebab-case): List components as kebab case
- [list-components-as-pascal-case](../bin/list-components-as-pascal-case): List components as PascalCase
- [list-implementations](../bin/list-implementations): List implementation directories
- [list-helper-packages](../bin/list-helper-packages): List one framework's top-level helper packages in dependency (build) order
- [check-port-parity](../bin/check-port-parity): Web Components helpers vs the HTML ones, Alpine vs Svelte: class hooks, events and attributes missing from the port, unless allow-listed with a reason
- [generate-comparisons](../bin/generate-comparisons): The component matrix in `compare/index.md` from `compare/compare.tsv` — `--check` (in bin/test) fails on drift, `--counts` prints each system's rows matched
- [generate-framework-matrix](../bin/generate-framework-matrix): The framework comparison, `docs/framework-comparison.md`: each headless catalog's package, versions supported, components, tests, stories, helpers, example app, skill and tutorial, read from the repository (`--check` in bin/test)
- [generate-bootstrap-migration](../bin/generate-bootstrap-migration): Generate and slug-check the Bootstrap migration mapping in the root guide and docs-site page (`--check` in `bin/test`)
- [generate-government-migration](../bin/generate-government-migration): Generate and slug-check the government-design-system-to-Lily mapping in `docs/migrating/government-design-system.md` (`--check` in `bin/test`)
- [check-port-data-attributes](../bin/check-port-data-attributes): Every port renders the `data-*` attributes Svelte renders, the state a theme or consumer CSS reads, unless `bin/check-port-data-attributes.allow.json` lists the gap with a reason; the list may only shrink (in bin/test)
- [check-port-logic](../bin/check-port-logic): Angular and Blazor vs Svelte: a port with no logic where Svelte has behaviour, and any Svelte prop missing from Angular, unless allow-listed with a reason; the list may only shrink (in bin/test). It finds a stub or a missing prop, it does not prove a port behaves the same
- [check-aria-baseline](../bin/check-aria-baseline): HTML and Blazor roots against `shared/aria-baseline.json`, what Svelte renders; the other catalogs compare in their render sweeps. The list may only shrink (in bin/test)
- [check-generic-names](../bin/check-generic-names): No HTML or Blazor component names a generic root, unless allow-listed with a reason; the list may only shrink (in bin/test). The other catalogs have a rendered `generic-name` test
- [check-generated-files](../bin/check-generated-files): The Generated files table above lists every generator and its `--check`, and none is missing or invented
- [check-package-metadata](../bin/check-package-metadata): Every published npm/NuGet package names the monorepo as its source repository — packages publish from the monorepo
- [create-component-directory](../bin/create-component-directory): Scaffold one component directory
- [create-implementation-directory](../bin/create-implementation-directory): Scaffold one implementation directory
- [test](../bin/test): Run all tests
- [sync](../bin/sync): rsync the root `AGENTS/` into every subproject except the helper packages (which keep their own helper `AGENTS/` set), `themes/` into the example apps and the docs site, and `NEWS.md` / `plan.md` into the site
- [sync-special-files](../bin/sync-special-files): Sync the top-level special files (LICENSE, CONTRIBUTING, SECURITY, GOVERNANCE, …) into every subproject
- [update](../bin/update): Start Claude Code with a standing "update, upgrade, fix, harmonize, audit, test" prompt over every subproject
- [generate-storybook-stories.mjs](../bin/generate-storybook-stories.mjs): Generate Storybook stories
- [publish-helpers](../bin/publish-helpers): Build and publish every helper package (npm / NuGet)
- [publish-headless](../bin/publish-headless): Build and publish the 7 full-catalog headless libraries, Web Components and Alpine (npm / NuGet)
- [publish-swift](../bin/publish-swift): Split `lily-design-system-swift/` and push it, with a never-moved semantic-version tag, to its read-only export repository (`make publish-swift TAG=0.1.0`); `--dry-run` splits only (SwiftPM needs `Package.swift` at a repository root)
- [publish-kotlin](../bin/publish-kotlin): Build and sign the Kotlin libraries and upload them to Maven Central's Portal staging API; `--dry-run` builds every publication into `build/repo` and checks each POM, with no credentials
- [generate-registries](../bin/generate-registries): Regenerate example-app catalog registries from components.tsv
- [check-links](../bin/check-links): Verify relative markdown links resolve
- [check-dtcg-tokens](../bin/check-dtcg-tokens): `themes/tokens/*.json` and `lily.resolver.json` are strict DTCG 2025.10 (in bin/test)
- [check-mobile-catalog](../bin/check-mobile-catalog): Every `components.tsv` slug has an Apple and an Android decision in `mobile/components-mobile.tsv` (`native`, `lily`, `pattern`, `none`, with a reason), and every ARIA name and HTML tag in the component AGENTS files has a SwiftUI, UIKit and Compose mapping in `mobile/semantics.tsv`; `--counts` prints the decisions (in bin/test)
- [check-native-primitives](../bin/check-native-primitives): Every Svelte overlay or popup component records its native-platform decision, in step with `spec/competitive-position/native-primitives.tsv` (in bin/test; `--write` regenerates the AGENTS.md sections)
- [check-dev-warnings](../bin/check-dev-warnings): Every interactive component with a required `label` warns when it is missing, in Svelte, React, Vue and Angular, unless allow-listed (in bin/test)
- [check-lifecycle](../bin/check-lifecycle): A `deprecated` or `discouraged` component names its replacement or its cited alternative, and `docs/adopters.md` names real components (in bin/test)
- [check-theme-references](../bin/check-theme-references): Report public-sector themes whose upstream package has a newer major release than `themes/references.tsv` records (report only, never fails on upstream)
- [generate-theme-contrast](../bin/generate-theme-contrast): The theme contrast table, every text pair in every reference theme against AA and AAA, as `docs/theme-contrast.md` and the site's `/theme-contrast` page (`--check` in bin/test)
- [generate-core](../bin/generate-core): The Lily Core tier from test, e2e and screen-reader evidence, the `/quality` page and the self-assessed ACR (`--check` in bin/test)
- [check-recipes](../bin/check-recipes): Every recipe in `recipes/{slug}/{name}.html` has front matter (title, components, tags), lists only real slugs it uses, parses, gives every control an accessible name, names only ids that exist, and never describes a control with a hidden element (in bin/test)
- [check-picker-icons](../bin/check-picker-icons): All 80 bundled picker icons follow the icon contract: one `viewBox`, a `currentColor` stroke, round caps and joins, `rem` size, `aria-hidden` (in bin/test)
- [check-theme](../bin/check-theme): Verify the 65 reference themes honour their conformance contracts; `--contrast` reports each theme's token-pair contrast against WCAG AA/AAA (report only)
- [check-class-names](../bin/check-class-names): Every headless implementation carries its kebab-case base class (first in a class list)
- [check-html-tags](../bin/check-html-tags): Every headless implementation's root element is the contract's HTML tag, or is listed with a reason in `bin/check-html-tags.allow.json` (which may only shrink; in bin/test)
- [check-identifier-validation](../bin/check-identifier-validation): Every national identifier type is validated by a function in `shared/national-identifiers.ts`, recorded as having no usable check with its reason, or listed open, in `shared/national-identifiers.tsv` (in bin/test)
- [check-component-guidance](../bin/check-component-guidance): Every component has a `- Purpose:` line in its `AGENTS.md` unless `bin/check-component-guidance.allow.json` lists it (the list may only shrink); every member of the notice and action prominence scales names its place in "When to Use"; the persuasive components name their misuse in "When Not to Use" (in bin/test)
- [check-known-limitations](../bin/check-known-limitations): Every canonical component `AGENTS.md` and `index.md` has one non-empty Known limitations section; also pins the disabled-link and look-alike guidance (in bin/test)
- [check-helper-docs](../bin/check-helper-docs): The Svelte grid-like helpers document every prop they have and list no shipped feature as a non-goal
- [check-label-packs](../bin/check-label-packs): Every label pack in `shared/label-packs` has the English pack's keys and placeholders, and the Svelte and TypeScript-port helpers still have every key the packs hold
- [verify-published](../bin/verify-published): After a publish, is every helper package's local version on its registry? `--wait` polls through registry lag
- [sync-shared-modules](../bin/sync-shared-modules): One source (`shared/`) for the pure modules the grid-like helpers copy (search, type-ahead, edit history, export, cell types, typed fields, direction, label coverage, dependency arrows, unavailable days, the filter model, the optional Gantt critical path, the label-pack loaders); `--check` (in bin/test) fails on drift
- [sync-example-components](../bin/sync-example-components): Mirror each headless library's components into its example app's copy; `--check` (in bin/test) fails on drift
- [check-identifier-inputs](../bin/check-identifier-inputs): Every national identifier input, in all nine catalogs, renders `autocomplete="off"` and `spellcheck="false"`, so the browser neither saves the value nor sends it to a cloud spellchecker (in bin/test)
- [check-solid-form-reset](../bin/check-solid-form-reset): Every bound `value` or `checked` in the Solid packages also binds `defaultValue` or `defaultChecked`, so a form reset does not clear it (Solid writes the property, never the attribute); `--write` adds them, and `convert-react-to-solid.py` calls it (in bin/test)
- [check-built-english](../bin/check-built-english): No headless component builds English around a value (`${label} (Step ${n} of ${total})`, a `=== 1 ? "file"` plural, `{count} selected` in markup), in all nine catalogs, unless `bin/check-built-english.allow.json` lists it with a reason; the list may only shrink (in bin/test). `check-worldwide` catches English defaults, this catches built strings
- [check-worldwide](../bin/check-worldwide): No single-region default in shipped code (a currency code, a `[0, 6]` weekend, an English locale), allow-list `check-worldwide.allow.json`; prints identifier and label-pack coverage by region (in bin/test)
- [check-coverage](../bin/check-coverage): Coverage drift matrix — per-component file presence across the 7 full-catalog headless libraries, plus a "keys" column that also covers Alpine and Web Components: a component whose `## Keyboard` names an APG key needs a test that sends a key, unless `bin/check-coverage.keys-allow.json` lists it with a reason, and a listed gap that is fixed must be removed (in bin/test)
- [test-generators](../bin/test-generators): Golden tests for four generators (in bin/test)
- [mutation-test](../bin/mutation-test): StrykerJS over the shared pure modules in `shared/`, each module's score against `shared/mutation-baseline.json`; fails on a drop (slow, so not in bin/test; `--update-baseline` after adding tests)
- [security-audit](../bin/security-audit): Known-vulnerability audit of every pnpm lockfile and published .NET project; fails on a high or critical advisory in what users install, reports the rest (weekly in `security-audit.yml`, not in bin/test)
- [coverage-report](../bin/coverage-report): Test coverage of `shared/`, Svelte headless and Blazor headless, written to `docs/coverage.md` and the badge `docs/coverage-badge.svg` shown in `index.md`, and checked against `coverage-floor.tsv`: more uncovered lines or branches than the floor fails, and fewer fails until `--update-floor` lowers it; `--floor-only` measures without writing (`bin/ci --job coverage-floor`). No coverage service; a few minutes, so not in bin/test
- [benchmark](../bin/benchmark): Performance benchmarks, each mean against a per-machine baseline: the shared pure modules at helper sizes (a 10,000-row grid, a 1,000-task Gantt chart) and, with `--suite render`, the Svelte data grid mounted, sorted and given new rows; fails beyond twice the baseline (machine-dependent, so not in bin/test)
- [render-benchmark](../bin/render-benchmark): Render-and-unmount cost of a Svelte headless button, input, listbox and table against equivalent hand-written markup, with the Lily/native ratio; fails beyond twice a per-machine baseline (machine-dependent, so not in bin/test)
- [generate-zone-names](../bin/generate-zone-names): `shared/zone-names/*.json`, CLDR time zone names per label-pack locale (`--check` in bin/test)
- [generate-mobile-tokens](../bin/generate-mobile-tokens): Swift and Kotlin tokens (sRGB colours, points and dp) for the first mobile themes, from `themes/tokens/*.json` (`--check` in bin/test)
- [generate-theme-tokens](../bin/generate-theme-tokens): DTCG token source under themes/tokens/ — extract, generate, drift-check
- [generate-component-categories](../bin/generate-component-categories): Regenerate components-categories.tsv (per-component HTML tag + category) from components.tsv
- [generate-page-markdown](../bin/generate-page-markdown): Localized `.md` twins for every site text page, plus a route audit whose reasoned exceptions may not go stale (`--check` in `bin/test`)
- [generate-api-docs](../bin/generate-api-docs): Canonical-contract sections on the site's component pages, generated from components/*/AGENTS.md — drift-checked
- [new-component](../bin/new-component): End-to-end scaffolder — one new placeholder component across every layer bin/test verifies
- [generate-examples](../bin/generate-examples): Usage examples (from the docs) and rendered variants (component-variants.json) for every demonstration page
- [extract-site-pages](../bin/extract-site-pages): The docs site's eight main English pages, and the further pages in `src/lib/extra-pages.json`, as translation sources (`src/lib/pages/*/en.html`)
- [check-site-page-translations](../bin/check-site-page-translations): Translated site pages keep the English markup structure and code samples, and each language is complete
- [generate-locale-pages](../bin/generate-locale-pages): `/<code>/<page>/` routes for every translated language
- [generate-site-pages](../bin/generate-site-pages): Docs-site component pages from components/{slug}/index.md, with the Example section refreshed on every page
- [sync-site-component-docs](../bin/sync-site-component-docs): Sync the docs site's per-component Markdown hand-off copies from the canonical component docs
- [sync-web-components-helpers](../bin/sync-web-components-helpers): Generate all 20 code-bearing Web Components helper pairs from their HTML custom-element sources, applying explicit stale-checked patches for genuine composition differences; `--check` gates every managed file in `bin/test`
- [dotnet-format](../bin/dotnet-format): Format or verify every Blazor library, test project and example app with `dotnet format whitespace`
- [generate-sitemap](../bin/generate-sitemap): Docs-site sitemap.xml from the route tree (`--check` reports drift)
- [ci](../bin/ci): The CI gate on the maintainer's machine: `--list`, `--job <name> [matrix value]`, `--fast` (the install-free checks) and `--full` (every job, in parallel lanes, a passed job cached while what it reads is unchanged; `--serial`, `--no-cache`), ending with a table of step, result and seconds. Each function is one job of `.github/workflows/ci.yml`, which calls `bin/ci --job <name>`, so the two cannot drift; `consumer-smoke` refuses to run locally unless `CI` or `LILY_CI_ALLOW_CONSUMER_SMOKE=1` is set. `--full` writes `.ci/receipt.json`, and `--verify-receipt` is the gate the publish scripts run before a real publish outside CI
- [setup-hooks](../bin/setup-hooks): Point `core.hooksPath` at `.githooks/`, whose `pre-push` runs `bin/ci --fast` before every push (opt-in, idempotent; `--undo` reverts; `git push --no-verify` skips one push)
- [smoke-packages](../bin/smoke-packages): Pack + install each published headless tarball into a scratch consumer and render it
