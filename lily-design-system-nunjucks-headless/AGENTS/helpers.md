# Framework helpers design principle rules

Each framework ships a `*-helpers` catalog of small, opinionated packages that sit alongside the headless library. Where a headless component is a pure container, a helper owns one complete interaction end to end. Most own a **user preference** — selection + DOM application + optional persistence. `share-picker` owns an **action** instead, and `date-time-picker` owns a **form value**: neither applies anything to the document and neither persists anything. They are all helpers because they ship the same headless contract and own the whole interaction, not because they share a lifecycle.

Full contracts: [spec/helpers/index.md](../spec/helpers/index.md).

## The helpers

Every catalog (html, svelte, react, vue, angular, blazor, nunjucks, and — since 2026-09-03 — web-components) ships all six. `lily-design-system-web-components-helpers` is a maintainer-directed **independent copy** of `lily-design-system-html-helpers` (which is itself already six vanilla custom elements) differing in tag prefix (`<lily-theme-picker>` rather than `<theme-picker>`, matching the Web Components headless catalog) and package naming; the two must be kept in step deliberately, since nothing ports between them automatically. As of 2026-09-03:

## Rules

- **One shape, across the five page-header helpers.** Each is an **icon button that opens a popup**, because a single glyph is the smallest possible footprint for a control that sits in a page header. The four preference helpers open a listbox; `share-picker` opens a disclosure of links. None may use the radio-group markup the June 2026 migration removed — do not reintroduce it. `date-time-picker` is exempt and only its trigger follows the rule: the reasoning behind "one glyph" is page-header footprint, which does not apply to a field in a form, and a date field that cannot be typed into is hostile to anyone who knows the date already.
- **Icon button + listbox contract (the four preference helpers).** Root `<div class="{helper} {class}">` containing a hidden input (form participation, carries `name`), a `<button class="{helper}-button" type="button" aria-label aria-haspopup="listbox" aria-expanded aria-controls>` whose only content is an `aria-hidden` glyph span, and a `<ul class="{helper}-list" role="listbox" tabindex="-1" hidden>` of `<li class="{helper}-option" role="option" aria-selected>`. Keyboard follows the WAI-ARIA APG listbox pattern: the open keys are ArrowDown / ArrowUp / Enter / Space, focus moves to the list, the cursor is `aria-activedescendant` (mirrored to `data-active` for CSS), arrows clamp rather than wrap, Home / End jump, printable characters typeahead over labels, Enter / Space select and return focus to the button, Escape closes without changing the value, Tab closes and moves on. A pointer selection does exactly what Enter does — selects, applies, **and closes** — so `aria-expanded` never survives the choice; a select-without-close leaves a stale `aria-expanded="true"` over a hidden list, and every later click misses the options. The consumer's `children` slot replaces the **glyph**, not the options.
- **`motion-picker`'s default differs from its three preference siblings.** `theme-picker` and `text-size-picker` resolve an unset value to a fixed slug (no OS signal exists for either). `motion-picker` instead checks the platform's own `(prefers-reduced-motion: reduce)` media query as one step of initial-value resolution — mapped to `"reduce"` / `"no-preference"` when the consumer offers those slugs — and does so **unconditionally**, not behind an opt-in flag like `theme-picker`'s `detectFromSystem`. Motion has a real accessibility signal (WCAG 2.3.3); deferring to it is the correct default, not an enhancement. In the Nunjucks port specifically, the check is unavailable at template-render time (no `matchMedia` on the server), so the macro marks `motions[0]` selected server-side and the client corrects it on init — documented as that catalog's one deviation from the canonical contract.
- **`share-picker` is a disclosure, not a listbox.** Its destinations are navigation, so they are real `<a>` elements: `role="menuitem"` would strip middle-click, open-in-new-tab and copy-link-address, and the APG itself suggests a disclosure when the items are links. Copy is a real `<button>`. Its list holds `{helper}-target` and `{helper}-copy` items rather than `role="option"` ones, and it carries a `{helper}-status` live region for the copy outcome. (Before the July 2026 rename it was `share-button`, and its trigger had to be `share-button-trigger` because `.share-button-button` read badly; the new name removes that exception, so the trigger is now plain `share-picker-button`.)
- **`share-picker` ships no endpoints.** No social-network URLs are bundled: which networks belong in a product is an editorial and privacy decision, and share URLs change. The consumer passes `targets`, each with its own `href(url, title, text)`.
- **Glyphs appear as bare literal characters in source, not escapes.** Code contexts hold the glyph itself directly in the string literal; markup contexts hold it directly too — no `\u` escape, no `\u{...}` codepoint escape, no HTML numeric entity. Reversed 2026-09-03 from the opposite rule: the glyph is visual, so a bare character is easy to type and easy to proofread by eye, where an escape like `"\u{1F310}\uFE0E"` has to be mentally decoded to confirm it even says "globe," and typing eight hex digits by hand invites a transposition an editor’s own glyph rendering would have caught on sight. ASCII `"A"` needs no change either way — it was already exempt. `bin/test` enforces this on the glyph constants and the icon markup.
- **The glyph is decorative.** It is wrapped in `aria-hidden="true"`; the accessible name comes from the button's `aria-label`. Never let a glyph be the accessible name — and remember the glyph is a font-dependent character, not a bundled asset. The glyphs are ◑ (U+25D1), 🌐 (U+1F310 + U+FE0E for text presentation), "A" (U+0041), ⏸ (U+23F8 + U+FE0E for text presentation), and ➤ (U+27A4). Prefer characters with real glyphs in ordinary font stacks: U+1F5DB was rejected for text-size because it falls back to a crude bitmap shape and means _decrease_ rather than _size_; U+23F8 was chosen for motion because media-transport symbols default to text presentation (unlike most pictographs) and read as "stop the moving parts."
- **Glyphs are optically matched, not merely equal-sized.** Different characters ink different fractions of their em box — measured on one baseline 2026-09-03 (plan P8-T10; max ink extent, "A" taken on width): ◑ 0.850, 🌐 1.000, "A" 0.675, ⏸ 0.495, ➤ 0.850 — so a single `font-size` looks wrong. The 45 `themes/*.css` correct each one via `--lily-picker-icon-scale` (1, 0.845, 1.25, 1.72, 1). Measure against the icon's _computed_ `font-family`, not a bare `system-ui` probe — the latter gives materially different ratios. `motion-picker`'s ⏸ was measured 2026-09-03 (plan P8-T8) by the same method — a real browser, the icon's *computed* font, ink extent over the em box — which first reproduced ◑ 0.850, 🌐 1.000 and "A" 0.675 against the documented 0.842 / 0.996 / 0.673; ⏸ inks 0.495, so its factor is 0.850/0.495 = 1.72. That reproduction also showed ➤'s former 1.268 had been measured under a different resolved face (against a U+25D1 of 0.777, not 0.842) and was not comparable; re-baselined to 1 the same day (plan P8-T10, a maintainer decision since it visibly changes the share icon in all 45 themes) — ➤ inks 0.850 wide, the same max extent as ◑.
- **Applying is idempotent.** A preference already applied is a no-op: no DOM write, no `localStorage` write, no change callback. Every framework reaches the apply step more often than the value actually changes — Svelte's `$effect` re-runs, the HTML element's `attributeChangedCallback` fires on any `setAttribute("value", …)` including an unchanged one, React applies once in controlled mode and again when the consumer writes the value back — and firing the callback each time invites the consumer to write state in it, which loops straight back in. In Svelte that loop ends in `effect_update_depth_exceeded`: the component stops updating its DOM entirely and the listbox freezes mid-open with a stale `aria-expanded`, which is not a symptom anyone reads back to a re-entrant apply. The callback contract is **once per applied change**, and the guard is what makes it true.
- **Headless still.** No bundled CSS, fonts, icons, images; kebab-case class hook + consumer `class` pass-through; rest-props spread on the root.
- **SSR-safe.** DOM writes only inside the framework's mount/effect lifecycle.
- **i18n-clean.** Every user-facing string is a prop; labels default to title-cased slugs with an override map (`themeLabels` / `localeLabels` / `sizeLabels` / `motionLabels`). `date-time-picker` takes one `labels` object instead of a dozen flat props — ten flat `*Label` props is a call site nobody can read — and takes month and weekday names from `Intl` rather than from a table. Its six structural labels are **required**, with no English default, because a nav button we named ourselves is exactly the defect the rule exists to prevent.
- **Spec-driven.** Each helper has a numbered `spec/index.md`; one test per acceptance clause.
- **Svelte is canonical.** Port contracts from `lily-design-system-svelte-helpers`; when catalogs disagree, the Svelte side wins.
- **Publishing.** Each helper is an npm package (`package.json`, `dist/` via the catalog `build.js`) — NuGet `.csproj` for Blazor — released with `bin/publish-helpers`. Each catalog and each helper is its own git subtree.
