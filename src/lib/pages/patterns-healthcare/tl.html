Mga user interface sa pangangalagang pangkalusugan

Gabay para sa mga koponang gumagawa ng clinical software gamit ang Lily: mga clinical portal, mga resulta at pag-uulat, pagrereseta at pagbibigay ng gamot, suporta sa pagpapasya at mga dashboard ng ospital.

Ang mga salin ng pahinang ito ay hindi pa nasusuring machine draft. Ang pahinang Ingles ang opisyal na bersyon.

Ang ginagawa ng Lily, at ang hindi nito ginagawa

Nagbibigay ang Lily ng mga kontrata sa pagpapakita: semantikong markup, ARIA, gawi ng keyboard at mga class hook para sa mga paulit-ulit sa mga clinical screen. Hindi ito nagbibigay ng clinical logic, clinical na nilalaman o pahayag ng regulasyon.

Regulasyon. Ang software na nagkakalkula ng marka, centile, dosis o interaksyon ng gamot ay karaniwang medical device. Wala sa mga ito ang kinakalkula ng Lily, sinadya. Kung regulado ang produkto ninyo, kayo ang may-ari ng usability engineering file nito (IEC 62366-1, ang gabay ng FDA sa human factors, EU MDR). Ang mga pagsusuri ng Lily, ang sariling-tayang ulat ng pagsunod nito sa accessibility at ang screen-reader matrix nito ay maaaring maging ebidensya sa file na iyon; wala sa mga ito ang pahayag ng pagsunod, at wala pang resulta ang matrix.

Mga alerto: mang-istorbo lamang para sa kritikal

Problema sa kaligtasan ang alert fatigue: kapag nang-iistorbo ang bawat alerto, binabalewala ng mga tao ang lahat. Ang gabay ng AHRQ ay iantas ang mga alerto ayon sa tindi at gawing nakaka-istorbo lamang ang malulubha.

  • Impormasyon (indicator="info"): nasa linya, katabi ng gawain, isang decision-support card sa pahina.
  • Babala (indicator="warning"): nakikita nang hindi humaharang, ang parehong card, may estilong namumukod; walang modal.
  • Kritikal (indicator="critical"): ilagay ang card sa loob ng alert dialog, at maglaan ng overrideReasons para humingi ng dahilan kapag ito ay isinara.
  • Ang decision-support card ay hindi kailanman live region nang mag-isa. Ipabatid ang bagong kritikal na card sa paglipat ng focus papasok sa dialog, hindi sa pamamagitan ng aria-live.
  • Alisin ang card kapag nangyari muli ang pangyayaring sinagot nito, at itala ang bawat kinalabasan (tinanggap, o nilampasan kasama ang dahilan).

Mga pagkakamali sa maling pasyente: kilalanin, huwag higpitan

  • Magpakita ng dalawang identifier saanman lumilitaw ang datos ng pasyente: ang pangalan kasama ang petsa ng kapanganakan, at ang pambansang identifier kasama ang view component nito (The Joint Commission, Quick Safety 45).
  • Gamitin ang patient banner sa bawat screen na kumikilos sa talaan ng isang pasyente, at panatilihin itong nakikita.
  • Bago ang aksyon sa talaang iba sa nasa banner, kumpirmahin ito gamit ang pangalan, petsa ng kapanganakan at identifier.
  • Ang entry tungkol sa ibang tao maliban sa pasyente (kasaysayan ng magulang, fetus, donor) ay unang nagsasabi sa salita kung kanino ito: bigyan ang mga item ng rekord ng subjectLabel ("Ina"), para hindi kailanman mabasa ang diyagnosis ng kamag-anak bilang sa pasyente (openEHR PARTY_RELATED, FHIR FamilyMemberHistory).
  • Huwag limitahan kung ilang talaan ang maaaring buksan ng clinician: natuklasan ng isang randomised trial ng 3,356 clinician (JAMA, 2019) na hindi nito binawasan ang maling order sa pasyente, at humahanap ng paraan ang mga tao para lampasan ito.
  • Ang menu ng mga aksyon sa isang rekord ay unang pinangangalanan ang rekord na iyon, gamit ang subjectLabel sa context-menu o dropdown-menu ("Ada Lovelace, presyon ng dugo Nob 3"): isang hindi interaktibong unang bahagi na siya ring accessible na pangalan ng menu.
  • I-uri ang bawat aksyon ayon sa ginagawa nito, at ipakita ang antas bago ito tumakbo. Karaniwan (tingnan, i-print) ay tumatakbo agad. Nakadokumento ay nagsasabi kung ano ang isusulat nito sa rekord ("Nagdaragdag ng tala sa konsulta"). Klinikal (itigil, kanselahin ang order) ay nagtatanong ng ikalawang beses, sa isang alert-dialog na ang button ng pagkumpirma ay ang pandiwa ("Itigil"), hindi kailanman "OK" o "Oo". Naglalantad (pang-emergency na access, pagbabahagi sa labas ng care team) ay humihingi muna ng dahilan at itinatala ito.
  • Kapag maraming rekord ang bukas (mga tab, window, hating panel), ang nakikitang teksto at accessible na pangalan ng bawat tab ay may pangalan ng pasyente at ikalawang identifier, inuulit ng aktibong panel ang banner, at walang aksyon na tumatama sa pasyenteng iba sa pasyente ng panel nito.
  • Ipakita bilang teksto sa header ng pahina ang lokasyong pagtatalagahan ng mga rekord (ang ward, klinika o pasilidad na pinili sa pag-sign in), at gawing malinaw na aksyon ang pagpapalit nito.
  • Ipakita ang aktibong pagbisita, o "Walang aktibong pagbisita", sa banner. Ang form na nangangailangan ng pagbisita ay nagsasabi nito at nag-aalok na magsimula ng isa, sa halip na pumalya kapag sine-save.

Ang patient banner

Nakadokumento ang komposisyon sa medical-banner, may gumaganang pahina sa /patient-banner sa SvelteKit example app:

  • dalawang identifier, at ang edad sa tabi ng petsa ng kapanganakan;
  • mga allergy sa pamamagitan ng allergy list, para ang "walang kilalang allergy", "hindi naitala" at "hindi magagamit" ay hindi kailanman magmukhang magkakapareho;
  • ang nawawalang halaga ay mga salita ("Hindi alam"), hindi tandang pananong, gitling o walang lamang cell;
  • isang pasyenteng pumanaw: data-deceased para sa theme, at isang nakikitang linya ng teksto, hindi kulay lamang;
  • walang field na pinutol, tinabas o itinago sa anumang lapad; bumabalot ito.
  • ang mga flag ng pasyente ("Kailangan ng interpreter", "Panganib ng impeksyon") ay isang may label na tag-group ng mga salita, hindi kailanman icon o kulay lamang, at nananatiling nakikita kapag bumalot ang banner.

Mga resulta

  • Iisang display para sa resulta, saanmang sistema ito nanggaling: ang observation view.
  • Ang flag ay mga salita mula sa salin ninyo (flagLabel), kasama ang interpretation code ng FHIR bilang data-interpretation para sa theme.
  • Ihiwalay ang mga bagong resulta sa mga nauna, at magpakita ng trend (isang sparkline, o line chart na may data table nito): hinahanap ng mga clinician ang makabuluhang pagbabago, hindi lamang ang saklaw.
  • Magkaibang kalagayan, na may magkaibang salita, ang resultang hindi kailanman naitala at ang resultang hindi magagamit.
  • Ang hindi alam ay hindi normal. Ang resultang walang reference range, naglo-load pa, o hindi mabasa ay walang interpretasyon at sinasabi ito; observation-view ay hindi kailanman naghihinuha, kaya ang resultang may range at walang interpretation ay walang ipinapakitang flag.
  • Ang resultang lampas sa iskala ay ang hangganan ng instrumento na may comparator ("> 33.3 mmol/L": formatQuantity na may ">") at ang iyong critical flag, hindi kailanman hubad na numero. Pinapanatili ng tantiyang halaga ang ≈ nito ("~").
  • Ibigay ang iba pang may pangalang range ("Kritikal: mas mababa sa 2.5") bilang ranges, bawat isa ay sariling bahagi.
  • Ang itinama o binagong resulta ay nagpapanatili ng halagang pinalitan nito, sa isang <del>, kasama ang iyong mga salita kung kailan ito nagbago (previousValue, previousLabel), para malaman ng clinician na nakabasa ng lumang halaga na nagbago ito.
  • Ang interval na pagbasa ay nagsasabi ng lapad at function nito ("Mean, 24 oras"), at ang estado at paraan ng pagbasa ("Nakaupo, malaking cuff") ay nakikitang teksto sa tabi nito, hindi kailanman tooltip lamang (openEHR INTERVAL_EVENT, state, protocol).
  • Ang trend ay nangangailangan ng maihahambing na punto: huwag gumuhit ng linya sa ibaba ng iyong minimum, putulin ang linya kung saan nagbago ang paraan o assay, at sabihin ang direksyon at kahulugan sa salita ("bumababa, bumubuti").
  • Ang vitals na inilagay sa isang sistema ng yunit ay maaaring magpakita ng iba sa tabi nito bilang iyong teksto ("70 kg (154 lb)"); walang kino-convert ang Lily, kaya sabihin ang iyong rounding. Maglagay ng dami gamit ang quantity-input-div, na ang numero ay sumusunod sa hangganan ng bawat yunit.
  • Ang growth chart ay isang line-chart na may mga centile line mo bilang series, mga punto ng bata at ang data table nito ng edad at halaga; walang kinukuwentang centile ang Lily at walang ibinibigay na growth reference.

Mga gamot

  • Mga generic na pangalan sa maliliit na titik, maliban sa mga titik na tall man mula sa mga listahan ng FDA at ISMP o ng inyong bansa (naglalathala ng sarili nila ang Australia at Canada). Markahan ang mga ito sa nameSegments; hindi kailanman hinuhulaan ng Lily.
  • Isulat ang lakas gamit ang formatQuantity: walang trailing zero, may leading zero, at no-break space bago ang yunit.
  • Panatilihin ang comparator ng resulta: ang formatQuantity(5, "mmol/L", locale, "<") ay nagsusulat ng "<5 mmol/L". Ang Quantity.comparator ng FHIR ay isinusulat na <, ≤, ≥ o >; kapag inalis ito, ang "mas mababa sa 5" ay nagiging "5".
  • Isulat ang mL, hindi cc, at iwasan ang bawat daglat sa listahan ng ISMP na madaling magkamali.
  • Huwag kailanman putulin ang pangalan o dosis ng gamot.

Mga petsa at oras

  • Isulat ang buwan bilang teksto para hindi mabasa ang petsa sa dalawang paraan (Intl.DateTimeFormat na may month: "short").
  • Piliin ang orasan nang sinasadya: ipasa nang tahasan ang hourCycle. Hinihingi ng NHS ang 24-oras na orasan; tuntunin iyon ng UK, hindi pandaigdigan, kaya hindi kailanman pinipili ito ng Lily para sa inyo.
  • Sinusunod ng mga edad ang mga banda ng Common User Interface sa pamamagitan ng ageParts(); ang serbisyong may ibang kaugalian ay nagpapasa ng sarili nitong mga salita.
  • Ang petsang alam lamang hanggang buwan o taon ay nananatiling ganoon: hingin ito gamit ang date-field precision="month" o "year", i-store ang 2019-03 o 2019, at isulat ito gamit ang formatPartialDate(). Huwag kailanman mag-imbento ng araw.
  • Ang tagal ng panahon ay duration-view, isang <time datetime="P3DT4H"> na naglalaman ng iyong mga salita, mula sa durationParts() at Intl.DurationFormat.

Mga dashboard

  • Madalas ma-update ang ward board o screen ng command centre. Huwag ianunsyo ang bawat pagbabago: magtago ng isang magalang na summary region ("3 kama ang bakante, 2 paglabas ang inaasahan") at hayaang basahin ng mga tao ang board.
  • Ang bawat estado sa board (malinis ang kama, may okupante, nakaharang) ay teksto o estadong data-* na may mga salita, hindi kulay lamang.
  • Walang kumikislap (WCAG 2.2.2, 2.3.1), at ang board na nag-a-update sa timer ay may pause control o nag-a-update lamang kapag hiniling; hindi kailanman inililipat ng update ang focus. Ang entry na lampas na sa oras ay nagsasabi nito sa salita ("Naghihintay nang higit 20 minuto") na may data-overdue.
  • Ang bilang o rate ay nagpapakita ng denominator nito ("12 sa 68") at nagli-link sa listahan sa likod nito.
  • Ang listahan o timeline ay nagsasabi kung ano ang tinitingnan nito: ano ang ipinapakita, ang ayos at saklaw na panahon nito, ano ang nakatago at bakit, at aling mga pinagmulan ang hindi sumagot. Ang walang laman na listahan mula sa pinagmulang hindi sumagot ay hindi patunay na walang umiiral.
  • Ang listahan ng paalala ay isang record-list na ang mga item ay may due date (review-date) at due state sa salita, na may data-due; ang patakarang gumawa nito ay sa iyo.

Mga form

  • Ang tanong na sinasagot ng "oo", "hindi" o "hindi tinanong" ay isang radio-group ng tatlong sagot, walang pinili sa simula, hindi kailanman checkbox: hindi matutukoy ng checkbox ang "itinanggi" mula sa "hindi kailanman tinanong". Ang review of systems ay isang fieldset bawat sistema ng katawan, at ang button na "lahat ng iba ay wala" ay nagtatakda lamang ng mga hindi pa nasasagot.
  • Ang tanong na may listahan ng sagot (gamot, address) ay isang repeatable-fieldset: idinaragdag o inaalis ang item, sumusunod ang focus, at bawat remove button ay ipinangalan sa item nito.
  • Numerong may decimal comma: ipakita ito gamit ang Intl.NumberFormat at, kung saan hindi tinatanggap ng type="number" ang comma, tanggapin ito sa text field na may inputmode="decimal" at i-parse sa iyong code. Huwag kailanman baguhin ang halagang tinype ng tao, kahit para ikulong sa range: ang halagang lampas sa range ay error na makikita nila.
  • Ang mahabang listahang nagre-render lamang ng bahagi ng mga opsyon nito sa bawat oras ay nagtatakda ng aria-setsize at aria-posinset sa bawat opsyon, at tinatandaan na hindi nakikita ng find-in-page ang natitira.

Mga rekord, tala at ang pinagmulan nila

  • Sabihin kung ano ang tinitingnan ng listahan o grid, bago ang mga row nito: ang saklaw na panahon at ayos, ano ang iniiwan at bakit, at aling mga pinagmulan ang hindi sumagot ("Huling 12 buwan, pinakabago muna. Hindi sumagot ang rekord ng GP."). Bigyan ang record-list at timeline-list ng coverageLabel, at ang data-grid helper ng sarili nitong coverageLabel. Ang walang laman na listahan mula sa pinagmulang hindi sumagot ay nagsasabi nito sa salita, para hindi kailanman mabasa bilang "walang naitala".
  • Sabihin kung saan nagmula ang rekord at kung pinal na ito gamit ang record-provenance-view: pinirmahan, naghihintay ng pirma, binago, naka-save sa device na ito at hindi pa naipapadala. Ang hindi pinirmahang draft ay hindi dapat magmukhang pinirmahan.
  • Ang entry tungkol sa iba (magulang, fetus, donor) ay unang nagsasabi kung kanino ito, gamit ang subjectLabel.
  • Ang pinigil na entry ay nananatili sa listahan kasama ang iyong mga salita ("Restricted: hindi available sa iyo"), at ang entry na nagawa nang mali ay nananatiling may guhit na "Naipasok nang mali": bigyan ang record-list-item o timeline-list-item ng entryState at ng entryStateLabel. Huwag kailanman alisin nang tahimik ang alinman, dahil ang puwang ay binabasang "walang nangyari".
  • Sa clinical note, markahan ang pinagmulan ng bawat bahagi (tinype, idinikta, template, kinopya pasulong, ginawa ng makina) gamit ang data-source at nakikitang salita, para hindi kailanman mapagkamalang pagsusuri ngayong araw ang kinopya o ginawang teksto.
  • Ang seksyong hindi ma-load ay unavailable sa iyong mga salita, na may retry button; ang teknikal na code, kung ipapakita man, ay nasa likod ng disclosure. Ang pagkabigo na sanhi ng aksyon ng tao ay inaanunsyo, kasama ang halagang hawak ngayon ng rekord; ang pagkabigo sa pag-load ng pahina ay hindi.
  • Ang kasaysayan ng order ay isang timeline-list, isang item bawat hakbang (planado, naka-iskedyul, aktibo, suspendido, kumpleto, kinansela) kasama ang oras at dahilan nito, at ang kasalukuyang estado rin sa item.

Mga naka-code na halaga

  • Ipakita ang Coding.display; kung wala, ang CodeableConcept.text; kung wala ang dalawa, ang system|code. Huwag kailanman mag-iwan ng walang lamang cell.
  • Magbigay ng kontrol na nagpapakita ng code system at code sa tabi ng bawat halaga, tulad ng toggle button na nagsasabing "Ipakita ang mga code". Nananatili sa labas ng reading order ang mga nakatagong code hanggang maipakita.
  • Markahan ang clinical text ng wika ng dokumento (lang), na maaaring iba sa wika ng interface. Isalin ang interface; huwag kailanman isalin ang clinical na nilalaman.
  • Walang kasamang terminolohiya ang Lily: walang paghahanap sa SNOMED CT, LOINC, ATC o UCUM. Isulat ang sinasabi ng dokumento. Ipinapakita ng pahinang /patient-summary ng halimbawa sa SvelteKit ang pattern.

Ang hindi gagawin ng Lily

  • Magkalkula ng early warning score, growth centile, dosis o saklaw ng sanggunian.
  • Maghatid ng database ng gamot, listahan ng tall man, o mga code ng SNOMED CT, ICD, LOINC o UCUM.
  • Kopyahin ang lisensyadong instrumento (Wong-Baker FACES) o ang disenyo ng ibang katawan (ang tsart ng NEWS2).
  • Limitahan ang bilang ng mga talaang sabay na bukas.
  • Maghinuha ng interpretasyon mula sa range, mag-convert ng yunit, o mag-parse ng relatibong petsa ("sa susunod na Martes").
  • Gumamit ng switch para sa "oo, hindi o hindi alam": ang switch ng ARIA ay walang ikatlong estado, kaya tatlong radio ito.

Ang pananaliksik, mga pinagmulan at mga pasya sa likod ng gabay na ito ay nasa spec/healthcare-ui.
