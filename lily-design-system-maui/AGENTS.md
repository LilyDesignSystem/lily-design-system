# Lily Design System: .NET MAUI — AI coding help

Read [spec/dotnet-maui](../spec/dotnet-maui/index.md) first, then [mobile/semantics.tsv](../mobile/semantics.tsv) (ARIA to the
platforms) and [mobile/components-mobile.tsv](../mobile/components-mobile.tsv) (what each component is on mobile).

- Two libraries, both net11.0: `LilyDesignSystem.Maui.Core` (pure C#, namespace `LilyDesignSystem.Maui.Core`) and
  `LilyDesignSystem.Maui` (controls on `Microsoft.Maui.Controls`, namespace `LilyDesignSystem.Maui`). No handlers, no platform
  code, so neither needs the MAUI workload to build or test.
- `Core/Shared/*.cs` is generated by `bin/sync-maui-core` from the Blazor headless library: edit the Blazor file, never the copy.
- A control is a MAUI view (usually a layout) with `BindableProperty` properties; text is `string` properties set by the app;
  slots are `View` properties (`Control`, `Body`, `Icon`). The root's `StyleClass` is the component's kebab-case slug, and
  each part's is the web's sub-class.
- Accessibility decisions that can be computed live in `LilySemantics` (Core) and are tested there; each control has a test per
  contract clause that reads `SemanticProperties` and `AutomationProperties`. Announcements go through `LilyAnnouncer.Current`;
  tests use `RecordingAnnouncer` in the `announcer` collection.
- Build a native control only where the mobile decision is `lily`; for `native`, document the MAUI control to use instead; the
  rest of the catalog is reached through Blazor Hybrid.
- Same names as Swift and Kotlin (`LilyAlert`, `LilyBadge`, `LilyCard`, `Tag`, `Field`, …), so the three mobile ports read alike.

Verify: `dotnet test LilyDesignSystem.Maui.slnx`, and `bin/test` from the monorepo root.
